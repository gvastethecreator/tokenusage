# Z.ai GLM Coding Plan quota gate

Cutoff date: 2026-07-21

Decision: `block`

## Question

Can a public Windows app query remaining GLM Coding Plan quota with an API key the user supplies, through an interface documented for region, account, and third-party use?

## Answer

Z.ai offers an official quota query for the Personal plan, but it publishes it as a plugin for Claude Code. It does not publish those endpoints in its general OpenAPI, and it does not expressly authorize a standalone desktop app. TokenUsage will not implement the Z.ai client or ask for its API key while a public contract for that use, or written permission, is missing.

The gate stays blocked, with the option to reopen it. The source exists; its current scope does not cover our product.

## Delegation and review

Grok Build did local forensics without the web and proposed `block`. The result is in `.scratch/agent-cli-delegation/grok-build/runs/2026-07-22T00-16-55-621Z-plan-7b7238f2/result.json`: `EndTurn`, seven turns, and USD 0.2202356 reported by the local CLI.

The parent review found the official plugin published after the upstream cutoff, pinned its commit, and reopened all primary sources. That finding changed the evidence: the endpoint already has an official implementation, with scope limited to Claude Code. The decision stays blocked because TokenUsage lacks a contract.

## Findings

### Quota

The official plugin proves that Z.ai exposes usage and quota data. Its documentation pins two scope limits:

- Personal plan;
- execution inside Claude Code.

The official script uses these bases by account:

| Account | Base |
|---|---|
| international Z.ai | `https://api.z.ai` |
| BigModel China | `https://open.bigmodel.cn` |

On each base it queries:

- `/api/monitor/usage/model-usage`;
- `/api/monitor/usage/tool-usage`;
- `/api/monitor/usage/quota/limit`.

The public repository shows an implementation, but the general OpenAPI does not offer schema, compatibility, permissions, or a retirement cycle for those paths.

### Authentication and permissions

The plugin uses `ANTHROPIC_AUTH_TOKEN` and derives the region from `ANTHROPIC_BASE_URL`. The reviewed sources do not define read-only scopes for a separate app or a key limited to quota. TokenUsage would have to store a key able to use the plan, with more permission than the data it seeks.

### Permitted use

The terms talk about consuming plan benefits and do not describe in a concrete way a quota read from another app. Even so, the documentation limits the official plugin to Claude Code, and the policy warns about unsupported tools and integrations. We infer that permission for TokenUsage is not established. Our gate requires clear permission and therefore fails closed.

### Spend alternative

The public OpenAPI does not offer account billing or usage. The `usage` values returned by a model response cover only that call and require the client to take part in it. TokenUsage will not make model calls to measure spend.

The local engine can attribute tokens and estimated cost to Z.ai models when a supported agent already records them. That view will be `Observed local usage`, with coverage, and not a Z.ai quota or invoice.

## Product decision

- Do not create a remote Z.ai provider in the public beta.
- Do not request or store a Z.ai API key.
- Do not invoke the plugin endpoints or automate Claude Code.
- Do not copy the OpenUsage adapter.
- Allow the local engine to group observations of Z.ai models that come from admitted logs.
- Reopen the gate when Z.ai publishes a third-party quota API, an official TokenUsage integration, or written permission that covers endpoint, auth, region, and account.

## Remaining uncertainty

Z.ai can extend the plugin to other tools or add its paths to the OpenAPI. The decision belongs to the documentation at the stated cutoff and must be reviewed before a beta that announces Z.ai support.
