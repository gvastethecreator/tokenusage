# Microsoft Store submission runbook

This directory is the source of truth for publishing the packaged TokenUsage application through Microsoft Store as an MSIX app.

It intentionally separates the Store channel from the GitHub/direct channel:

```text
Microsoft Store
  -> Store-associated identity
  -> .msixupload preferred
  -> Microsoft re-signs after certification
  -> Store-managed updates

GitHub/direct
  -> portable ZIP or directly distributed package
  -> publisher-owned Authenticode signing
  -> publisher-owned update flow
```

Do not publish the portable ZIP as the Store package. Do not reuse a Store-associated raw MSIX as a public sideload package unless it is signed for that distribution scenario and the identity and update effects are reviewed.

The machine-readable source is [`store-identity.json`](store-identity.json).

| --- | --- |
| `Package/Identity/Name` | `GVASTETHECREATOR.TokenUsage` |
| `Package/Identity/Publisher` | `CN=DB97CC4C-CCCD-41DF-8D43-C67641CBBC92` |
| `Package/Properties/PublisherDisplayName` | `GVASTETHECREATOR` |
| Package Family Name | `GVASTETHECREATOR.TokenUsage_h2dcbfhqhrgv8` |
| Package SID | `S-1-15-2-1053362801-2461558768-657845133-3595218920-1529770649-1636304934-4044864160` |
| Store ID | `9NWX6M53B36K` |

Rules:

- `Name`, `Publisher`, and `PublisherDisplayName` must match Partner Center exactly.
- Never paste trailing spaces or non-breaking spaces into the manifest.
- The Package Family Name and Package SID are derived by Windows and Partner Center. They are verification values only and do not belong in `Package.appxmanifest`.
- Do not invent the Store deep link or public Web Store URL before Partner Center exposes them for the live product.

## Repository implementation

The Store identity is committed in:

```text
src/TokenUsage.Package/Package.appxmanifest
```

Store readiness is checked by:

```powershell
.\scripts\store\Test-StoreReadiness.ps1
```

A Store upload candidate is generated by:

```powershell
.\scripts\store\Build-StoreUpload.ps1 -Platform x64
```

The build script creates a `.msixupload` artifact using the MSBuild `StoreUpload` path. A short-lived self-signed certificate whose subject matches the Partner Center publisher can be generated only to complete package construction and local validation. Microsoft Store replaces the package signature after certification. This test certificate is not a public distribution credential.

## Submission sequence

### 1. Pricing and availability

Complete every required field:

- Markets: explicitly review the default market selection.
- Audience: use Public only when the first release is ready for unrestricted acquisition.
- Discoverability: choose discoverable or direct-link-only intentionally.
- Schedule: for the first submission, a manual publishing hold is recommended so certification approval cannot immediately expose an unreviewed listing.
- Base price: choose Free unless a commercial decision says otherwise.

Record the final choices in the release evidence document.

### 2. Properties

Recommended initial values:

- Primary category: Developer tools.
- Website: the public project or product website.
- Privacy policy URL: a stable public rendering of [`../../PRIVACY.md`](../../PRIVACY.md).
- Contact details: complete the company-account fields in Partner Center.
- Display mode: leave immersive/XR options disabled.
- System requirements: Windows 10 version 1809 or later; x64 for the first Store package unless ARM64 is validated and included.

TokenUsage reads local usage sources and can use opt-in local or remote provider connections. Even where the app does not transmit personal data by default, publish a privacy policy rather than relying on the optional-policy path.

### 3. Age ratings

Answer every questionnaire item. TokenUsage has no user-generated public content, gambling, violence, sexual content, or unrestricted web browsing. Preserve a PDF or screenshots of the completed questionnaire in private release evidence if operationally useful; do not commit Partner Center account screenshots containing unrelated account details.

### 4. Packages

Upload the `.msixupload` generated by the Store build.

Before upload, confirm:

- package identity matches `store-identity.json`.
- target device family is `Windows.Desktop` only.
- version is four numeric components and greater than every previously submitted applicable package.
- architecture is exactly what the listing and requirements claim.
- `runFullTrust` and the execution alias are shown in package details as expected.
- en-US is reported as the supported resource.
- no unsigned/direct-channel portable artifact is uploaded.
- no development certificate or `.pfx` is included in the submission artifact.

Partner Center can show a package as Validated while the Packages section remains Incomplete. Complete all package-related settings and device-family selections before treating the section as finished.

### 5. Store listings

Create listings for both supported languages:

- English (United States)
- Spanish (Spain), or the Spanish locale selected in Partner Center

Use [`LISTING.md`](LISTING.md) as the copy source. At least one screenshot is required. Four or more are preferred. Use real application screens. Avoid mock data that can look like fabricated provider support.

Required review points:

- description accurately distinguishes reported, estimated, partial, stale, unavailable, and unpriced data;
- screenshots do not expose usernames, paths, account identifiers, usage histories, API keys, or other personal data;
- provider names and trademarks are descriptive and do not imply endorsement;
- the listing does not promise live quota support for providers where the app only has local usage data;
- x64/ARM64 claims match uploaded packages.

### 6. Submission options

Use [`CERTIFICATION-NOTES.md`](CERTIFICATION-NOTES.md) as the copy source.

TokenUsage declares `runFullTrust`, so the restricted-capability explanation is required. Explain the concrete desktop operations rather than stating only that the capability is necessary.

For the first release:

- use a manual publishing hold;
- include test instructions for an environment with no supported provider installed;
- explain that empty/unavailable states are expected and are not an incomplete app;
- explain how to invoke the `tokenusage.exe` execution alias after installation;
- identify any provider integrations that require explicit opt-in;
- include the date of the certification notes.

## `runFullTrust` rationale

TokenUsage is a native desktop application and CLI. It needs full-trust desktop execution to:

- read bounded, documented local usage sources owned by installed AI developer tools;
- access local files and databases through normal Win32/.NET APIs;
- use Windows integrations such as Credential Locker and packaged local storage;
- run the packaged command-line executable exposed through `tokenusage.exe`;
- coordinate the tray application and local reporting workflows.

The capability is not used to bypass Windows security boundaries, copy another product's credentials, inspect prompts or responses, or silently transmit local content.

## Versioning

Source/product version uses `major.minor.patch`. MSIX identity uses four numeric components:

```text
0.0.1 -> 0.0.1.0
```

Release rules:

1. `Directory.Build.props` is the product-version source of truth.
2. The manifest version must be the corresponding four-part MSIX version.
3. Every submitted package applicable to the same users must have a greater version than the previous submission.
4. Pre-release suffixes such as `-rc.1` must not be placed in `Identity.Version`.
5. Store and direct artifacts built from the same commit must record the same product version even when their file names or signing identities differ.

## Test matrix

A Store candidate is not release-ready until these checks pass on a clean Windows profile or VM:

| Test | Required result |
| --- | --- |
| Install Store candidate/test package | Package installs without missing dependencies |
| First launch | Tray app launches and renders a valid empty or populated state |
| No-provider environment | Honest unavailable/empty state, no crash, no fake usage |
| Local provider present | Reader detects only documented data |
| CLI alias | `tokenusage doctor --format human` resolves after installation |
| Language | English-only UI remains usable |
| Upgrade | Existing LocalState data is preserved |
| Uninstall | Package removes cleanly without corrupting portable data |
| Reinstall | App starts from a clean package state |
| Standard user | Normal use does not require administrator privileges |
| Offline launch | App starts and explains unavailable remote/opt-in data |
| Privacy review | Logs and diagnostics contain no credentials or customer content |

## Release gates

A submission is blocked until all items are true:

- [ ] Store identity validator passes.
- [ ] Full repository check passes on the submission commit.
- [ ] `.msixupload` is generated from the submission commit.
- [ ] Artifact hash and source commit are recorded.
- [ ] Clean install, launch, CLI alias, upgrade, uninstall, and reinstall are evidenced.
- [ ] Privacy-policy URL is public and stable.
- [ ] English listing copy matches the English-only UI. Spanish listing copy is reviewed as a Partner Center locale.
- [ ] Screenshots are current and scrubbed of personal information.
- [ ] Age rating is complete.
- [ ] `runFullTrust` explanation is entered.
- [ ] Certification notes match the shipped build.
- [ ] Publishing hold is configured intentionally.
- [ ] Final package details in Partner Center show only expected architectures, languages, and capabilities.

## First-submission operating procedure

1. Merge the Store-readiness changes.
2. Tag or otherwise freeze the submission commit.
3. Run the full release check.
4. Generate the `.msixupload` with `Build-StoreUpload.ps1`.
5. Record SHA-256, size, version, architecture, and commit in a copy of [`RELEASE-EVIDENCE-TEMPLATE.md`](RELEASE-EVIDENCE-TEMPLATE.md).
6. Test installation lifecycle on a clean machine.
7. Start a draft submission in Partner Center.
8. Complete Pricing and availability, Properties, Age ratings, Packages, Store listings, and Submission options.
9. Upload only the reviewed `.msixupload`.
10. Resolve every package warning or document why it is non-blocking.
11. Submit with a manual publishing hold.
12. Review the certification report and listing preview.
13. Publish only after you check the released Store package, listing, privacy URL, support path, and analytics configuration.

## Non-automatable account steps

The repository cannot safely automate these decisions without Partner Center credentials and product-owner review:

- market selection and pricing;
- company contact details;
- age-rating answers;
- final screenshot upload;
- privacy-policy URL ownership verification;
- restricted-capability approval text submission;
- certification submission and publishing hold release.
